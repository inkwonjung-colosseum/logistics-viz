쇼핑몰마다 다른 주문을 어떻게 한 형식으로 받는가

판매 채널 연동 · 주문 수집

상품을 파는 창구가 판매 채널이다 — 자사몰, 마켓, 매장. 채널마다 주문 서식이 달라, 모아서 한 형식으로 만드는 주문 수집이 없으면 채널마다 주문을 하나씩 옮겨 적어야 한다.

처음이라면 — 이 페이지가 전제하는 말 3개

API·EDI(외부 연동) — API(Application Programming Interface)는 프로그램끼리 정해진 규칙으로 데이터를 주고받는 연결 창구다. EDI(Electronic Data Interchange, 전자 문서 교환)는 회사 사이에 주문·통지 같은 문서를 정해진 서식으로 주고받는 방식이다. → 외부 시스템 연동 (EDI · API)

주문 상태 — 주문이 접수된 뒤 배송이 끝날 때까지 어디까지 진행됐는지 나타내는 표시다. 이 페이지에서 모은 주문이 이 상태로 여정을 시작한다. → 주문 한 건의 여정 (주문 상태 라이프사이클)

상태 매핑 — 창고의 세부 작업 상태를 화주에게 보여 주는 주문 상태로 옮겨 놓은 대응표다. 매핑은 한 체계의 코드를 다른 체계의 코드로 이어 주는 대응표다. → 상태 매핑 (창고 작업 상태 → 화주용 주문 상태)

판매 채널(sales channel) — 상품을 파는 창구다. 자사몰, 마켓, 오프라인 매장이 각각 채널이다.

주문 수집(order intake) — 여러 채널에서 들어온 주문을 한 시스템에 모아 한 형식으로 만드는 일이다.

비유 — 멀티 채널 메신저 · 카톡·문자·메일로 흩어진 약속을 캘린더 하나에 옮겨 적는다. 어디서 왔든 캘린더 칸 형식은 하나라 다음 일정을 볼 수 있다. 맞지 않는 지점이 하나 있다 — 메신저는 답장만 하면 되지만 주문은 재고까지 묶어야 한다.

왼쪽 세 상자 = 판매 채널(화주색 — 상품을 파는 주체의 색). 가운데 = OMS(운영사색)의 주문 수집 · 매핑 · 필수 검증. 오른쪽 = 만들어진 표준 주문서. 화살표 라벨 = 채널 접속 방식이고, "전부 수기 등록"을 고르면 사람이 점선 화살표로 옮겨 적는다.

채널 주문 카드 — 하루 15건 도착

    표준 필드자사몰 · API마켓 A · EDI마켓 B · 엑셀
    주문번호주문번호ORD_NO주문 ID
    SKUSKUSKU_CD상품 번호
    수량수량QTY갯수
    수취인 전화번호 (필수)수취인 전화RCV_TEL휴대폰

    같은 값이 채널마다 다른 이름으로 온다 — OMS는 이 대응표(매핑 규칙표)를 채널마다 설정해 표준 형식으로 바꾼다. 단, 매핑은 이름을 바꿔 줄 뿐 빈 값을 채워 주지는 않는다 — 마켓 B의 빈 전화번호 칸은 매핑으로도 못 채우고, 필수 항목 검증이 걸러 낸다. 현실에서는 채널이 API·EDI를 열어 주지 않으면 수기 등록이 유일한 방법이라, 수집 방식은 선택이 아니라 채널의 조건이 되기도 한다.

    전제: 하루 주문 15건 · 채널 3개, 서식 차이는 대표적인 경우(표준 필드 · 코드형 EDI · 이름 제각각인 엑셀)로 단순화했다. 수기 등록의 오류·지연은 "옮겨 적다 1건(MA-3302)의 SKU를 잘못 적고, 마감(14시)에 3건을 놓친다"는 고정 시나리오(같은 조건이면 결과가 항상 같다)로 두었다.

    채널이 자동으로 연결돼 있으면 주문이 저절로 한 형식으로 모이지만, 필수 항목 검증이 없으면 빠진 주문이 배송 단계에서 터진다 — 수집과 검증은 세트로 움직인다. 그래서 실무에서는 채널 연동을 열 때 필수 항목 규칙을 함께 설정하고, 빈 칸은 배송 전에 보류로 걸러 낸다.

    시스템에서는 OMS에서는 채널별 접속 방식(API·EDI·업로드)과 필드 매핑, 필수 항목 규칙을 채널마다 설정해 주문을 표준 형식으로 만든다. 규칙은 운영사·채널마다 다르게 설정한다.

    선행: 외부 시스템 연동 (EDI · API) — 채널·창고·운송사와 문서를 주고받는 연결 방식
