# 학습 패턴 표준

개념 페이지 한 편을 만들 때 따르는 규격서다.
목표는 "읽는 사전"이 아니라 **질문을 들고 들어와 직접 만져 보고 답을 가지고 나가는 페이지**다.

- **읽는 사람**: 회사에 처음 들어온, 물류를 전혀 모르는 사람. 물류 용어를 하나도 모른다고 가정한다. 앞 페이지를 차례로 봤다면 막히는 말이 없어야 한다.
- **적용 범위**: 이 문서 이후에 만드는 페이지. 이미 배포된 페이지는 그대로 유효하며, 보강할 것은 `roadmap.md`에 작업으로 적는다.
- **문서 간 우선순위**: 색·타이포·애니메이션·접근성은 `design-tokens.md`가 우선한다. 이 문서는 학습 구조만 정한다.
- **무엇을 만들지**는 `roadmap.md`가 정한다. 그 표의 slug · 질문 · 형식이 페이지 기획의 출발점이다.

## 세 가지 원리

1. **질문에서 시작한다.** 정의부터 읽으면 남지 않는다. 누구나 떠올릴 수 있는 질문 하나를 먼저 던지고, 페이지 전체가 그 질문에 답한다.
2. **비교로 이해한다.** 개념을 혼자 설명하지 않는다. 다른 방식과 나란히 두거나 경쟁시켜야 차이가 보인다.
3. **만져서 확인한다.** 조건을 바꾸면 결과가 달라지는 것을 직접 봐야 "언제 무엇을 쓰는가"가 남는다.

## 페이지 구성

위에서 아래로 이 순서를 따른다.

| # | 요소 | 규칙 | 구분 |
|---|------|------|------|
| 1 | **질문** | `roadmap.md`의 질문을 `h1` 위 카테고리 줄에 이어서 쓴다 (별도 제목을 만들지 않는다) | 필수 |
| 2 | **정의** | `h1` + 한 줄 정의. 개념어는 굵게, 영문 용어는 처음 한 번 병기, 비유는 하나까지 | 필수 |
| 3 | **처음이라면** | 이 페이지가 전제하는 말을 최대 3개까지 한 줄씩 풀이하고 그 말을 소개한 페이지로 링크한다. 정의 아래 접힌 한 줄(`details`)로 둔다 | 전제하는 말이 있으면 필수 |
| 4 | **예측** | 체험 전에 "어느 쪽이 이길까?"를 고르게 하고, 결과가 나오면 맞았는지 알려준다. 선택 버튼은 컨트롤 행에 함께 둔다 | 권장 |
| 5 | **체험** | 체험 형식 5종 중 하나 | 필수 |
| 6 | **손잡이** | 2~3개. 값을 바꾸면 결과가 즉시 갱신된다 | 필수 |
| 7 | **숫자** | KPI 3개 이하. 승자와 패자를 이름으로 말한다 | 필수 |
| 8 | **전제** | 단순화한 가정을 한 줄로 밝힌다 | 필수 |
| 9 | **결론** | 질문에 대한 답 한 줄. "그래서 실무에서 ~한다"로 끝낸다 | 필수 |
| 10 | **시스템에서는** | 이 개념이 시스템에서 어떤 필드·상태·규칙이 되는지 한 줄. "OMS에서는" 또는 "WMS에서는"으로 시작하고, 운영사마다 다르게 설정하는 값이면 그렇게 밝힌다 | 필수 |
| 11 | **이어 보기** | 선행 개념과 다음 개념 링크 (완료된 페이지만) | 권장 |
| 12 | **완료 버튼** | `✓ 학습 완료` ("기술 계약" 참고) | 필수 |

첫걸음 트랙 페이지는 이 표의 일부를 완화한다 ("첫걸음 트랙 규칙" 참고).

```
┌ ← 카탈로그 ─ 카테고리 · 질문 한 줄
│ h1 · 정의 한 줄
│ ▸ 처음이라면 (접힘)
│ [체험 패널]
│ [예측 선택 · 손잡이 2~3개 · 재생/초기화]   한 행
│ [KPI 카드 ≤3]
│ 전제 한 줄
│ 결론 한 줄
│ OMS에서는 / WMS에서는 한 줄
│ 이어 보기
└ [✓ 학습 완료]
```

## 체험 형식 5종

개념에서 **움직이는 것이 무엇인가**로 형식을 고른다. 한 페이지는 형식 하나만 쓴다.

| 형식 | 움직이는 것 | 화면 | 필수 컨트롤 | 비교를 만드는 법 |
|------|-------------|------|-------------|------------------|
| **흐름형** | 물건 · 차량 · 작업자 | 공간 위 이동 애니메이션 | 재생 · 일시정지 · 초기화 | 방식 A와 B를 나란히 돌린다 |
| **릴레이형** | 주체 사이의 문서 · 이벤트 · 상태 | 주체별 레인과 메시지 화살표 | 재생 또는 이전 · 다음 단계 | 연동 있음 vs 수기 전달, 정상 vs 예외 |
| **배정형** | 결정 (어디에 · 누구에게 · 얼마나) | 후보 비교판과 배정 결과 | 정책 토글 | 같은 주문에 정책을 바꿔 적용한다 |
| **입력형** | 데이터의 품질 | 입력 폼과 뒤 단계의 영향 목록 | 항목 토글 · 프리셋 | 채움 vs 누락, 일치 vs 불일치 |
| **측정형** | 숫자를 세는 기준 | 원천 기록과 집계 결과 | 기준 토글 | 같은 실적에 기준을 바꿔 적용한다 |

- 형식이 애매하면 질문의 동사로 고른다: "어떻게 흐르나"는 흐름형, "누가 누구에게 넘기나"는 릴레이형, "어디에 맡기나"는 배정형, "무엇이 빠지면 멈추나"는 입력형, "어떻게 세나"는 측정형.
- **미니게임**은 배정형의 변형이다. 정책 대신 학습자가 직접 결정하고, 기준 정책의 점수와 비교해 준다.
- 흐름형·릴레이형의 애니메이션은 자동으로 시작하지 않는다 (`design-tokens.md`).

## 내용 원칙

- **공정한 비교**: 경쟁하는 방식들은 같은 주문·같은 재고·같은 시간을 만난다. 시드를 고정해 조건이 같으면 결과도 항상 같다.
- **살아 있는 손잡이**: 손잡이를 극단으로 움직이면 순위가 뒤집히거나 격차가 벌어져야 한다. 어떻게 움직여도 한쪽만 이기면 그 손잡이는 뺀다.
- **손잡이의 이름은 현장의 변수**: "파라미터 A"가 아니라 "주문당 품목 수", "창고 간 거리", "마감 시간"처럼 실무에서 실제로 바뀌는 값을 쓴다.
- **숫자는 단위와 함께**: 건당 비용(원), 소요 시간(분), 준수율(%)처럼 단위를 붙이고, 어느 쪽이 좋은 방향인지 드러낸다.
- **결론은 조건문**: "A가 좋다"가 아니라 "~할 때는 A, ~할 때는 B"로 쓴다. 손잡이로 확인한 내용과 일치해야 한다.
- **용어는 하나로**: 같은 대상을 페이지마다 다르게 부르지 않는다. 주체 이름은 "4PL 트랙 규칙"의 표를 따른다.

## 쉽게 쓰기

물류를 전혀 모르는 사람이 읽는다고 생각하고 쓴다. 모든 신규 페이지에 적용한다.

- **질문과 결론은 쉬운 말로**: 이 두 줄만 읽어도 뜻이 통해야 한다. 풀이 없는 약어나 전문용어를 쓰지 않는다. `h1`의 개념 이름에는 실무 용어를 그대로 쓴다.
- **새로 나오는 말은 5개까지**: 한 페이지에서 처음 소개하는 용어는 5개를 넘기지 않는다. 넘으면 페이지를 나눈다.
- **처음 나오는 자리에서 풀이한다**: 용어가 처음 나올 때 한 줄로 풀이하고 영문을 병기한다. 약어는 풀어 쓴다 — "WMS(창고 관리 시스템)".
- **풀이 문장은 용어집을 따른다**: 같은 말을 페이지마다 다르게 풀이하지 않는다. 풀이는 `docs/glossary.md`의 문장을 가져온다.
- **이미 배운 말은 "처음이라면"으로 잇는다**: 앞 페이지에서 소개한 말을 전제로 쓸 때는 다시 길게 설명하지 않고 "처음이라면" 줄에 풀이와 링크를 둔다.
- **비유는 일상에서 하나만**: 택배, 편의점, 식당 주방, 냉장고처럼 누구나 아는 것에서 고른다. 비유가 맞지 않는 지점이 있으면 한마디로 밝힌다.
- **예시 숫자는 한눈에 셀 수 있게**: 주문 10건, 창고 3곳, 상품 5종처럼 작게 잡는다.
- **한 문장에 새 용어 하나**: 처음 보는 말이 한 문장에 둘 이상 나오지 않게 한다.

## 첫걸음 트랙 규칙

첫걸음 트랙은 개념을 겨루는 페이지가 아니라 **전체 모습과 기본 말을 소개하는 페이지**다.
그래서 "페이지 구성"과 "내용 원칙"의 일부를 다음과 같이 완화한다.

| 항목 | 일반 페이지 | 첫걸음 트랙 |
|------|-------------|-------------|
| 새로 나오는 말 | 5개까지 | 3개까지 |
| 손잡이 | 2~3개, 순위가 뒤집혀야 함 | 1~2개. "있을 때 vs 없을 때"나 단계 이동만으로도 된다 |
| 숫자 | KPI 3개 이하, 승자를 말함 | 0~2개. 승자를 가리지 않아도 된다 |
| 결론 | 조건문 | 한 문장 요약이어도 된다 |
| 시스템에서는 | 필수 | 생략할 수 있다 (OMS·WMS를 아직 배우지 않은 독자) |
| 처음이라면 | 전제하는 말이 있으면 필수 | 전제하는 말을 두지 않는 것이 원칙 |
| 이어 보기 | 권장 | 필수. 다음에 볼 페이지 하나를 가리킨다 |

- 비유는 반드시 하나 넣는다.
- 주체가 나오면 "4PL 트랙 규칙"의 이름과 색을 그대로 쓴다. 뒤 페이지와 같은 그림으로 이어지게 하기 위해서다.

## 4PL 트랙 규칙

4PL 트랙 페이지는 "한 창고 안의 효율"이 아니라
**"주체 사이에서 무엇이 오가고, 누가 결정하고, 누가 책임지는가"**를 보여준다.

### 주체 표기

등장하는 주체는 이름과 색을 고정한다. 색만으로 구분하지 않고 항상 레이블을 함께 쓴다.

| 주체 | 하는 일 | 색 |
|------|---------|-----|
| **운영사** | 화주·창고와 계약하고 물량을 배정·감시한다 (페이지의 주인공). 자사일 수도, 자체 운영 고객일 수도 있다 | `--viz-series-1` |
| **화주** | 물건의 주인. 주문과 입고를 의뢰한다 | `--viz-series-2` |
| **창고** | 보관 · 피킹 · 출고를 실행한다 | `--viz-series-3` |
| **운송사** | 구간 운송과 배송을 실행한다 | `--viz-series-4` |

- 주체가 둘 이하면 `--viz-series-1`과 `--muted-foreground`만 쓴다.
- `--viz-series-1`이 운영사의 색이므로, 주체가 나오는 페이지에서 선택·활성 상태는 색이 아니라 테두리 굵기로 표시한다.
  `design-tokens.md`의 "활성 상태 → `--viz-series-1`" 규칙에 대한 명시적 예외다.
- 운영사가 둘 이상 등장하는 페이지(`tenant-structure` 등)는 "운영사 A", "운영사 B"로 이름을 붙이고 같은 색을 쓴다.

### 관점 토글

- "누가 어디까지 보는가"가 핵심인 개념에만 둔다 (`tenant-structure`, `order-handoff`, `control-tower` 등).
- 토글(화주 / 운영사 / 창고)을 바꾸면 **같은 사건의 보이는 범위**가 달라진다.
  예: 출고 지연 한 건 — 창고는 자기 작업의 지연만, 화주는 "배송 늦음"만, 운영사는 어느 창고·어느 구간에서 막혔는지와 대체 경로까지 본다.
- 손잡이 2~3개 한도에 포함된다. 다만 순위를 뒤집는 손잡이가 아니라 시야를 바꾸는 손잡이이므로 "살아 있는 손잡이" 원칙의 예외다.

### 숫자의 주인공

- 배정형: 건당 물류비, 약속 납기 준수율, 분할 출고율
- 릴레이형: 정보 지연 시간, 수작업 건수, 상태 불일치 건수
- 입력형: 자동 처리율, 보류 건수, 재작업 시간
- 측정형: **창고·운송사 간 비교**가 주인공이다. 한 곳의 숫자가 아니라 같은 기준으로 잰 여러 곳을 나란히 보여준다.

### "4PL 시점에서는" 박스 (완료된 실행 층 페이지 보강)

실행 층 페이지는 다시 만들지 않고 박스 하나를 덧붙여 4PL 트랙과 잇는다.
대상과 연결할 페이지는 `roadmap.md` "실행 층"의 "4PL 박스" 칸에 있다.

- 위치: 결론 아래, 완료 버튼 위
- 분량: 제목 "4PL 시점에서는" + 2~3문장 + 링크 하나
- 내용 (해당하는 것만):
  1. 이 작업의 결과 가운데 **OMS가 받아야 하는 것**은 무엇인가
  2. **운영사나 창고마다 다르게 설정**할 수 있어야 하는 것은 무엇인가
  3. 문제가 생기면 **누구 책임**으로 처리되는가
- 기존 체험·손잡이·숫자는 건드리지 않는다.
- 같은 페이지의 "쉬운 말 점검"도 이때 함께 한다.

## 페이지 기획서

제작에 들어가기 전에 이 칸을 채운다. 채워지지 않는 칸이 있으면 아직 만들 단계가 아니다.
slug · 질문 · 형식은 `roadmap.md`에서 그대로 가져온다.

```
slug          :
질문          :
정의          :
새로 나오는 말 : (5개까지, 첫걸음 트랙은 3개까지. 풀이는 glossary.md 문장)
처음이라면    : (전제하는 말 3개까지 → 그 말을 소개한 페이지)
비유          : (일상에서 하나)
형식          : 흐름형 | 릴레이형 | 배정형 | 입력형 | 측정형
비교 대상     : (무엇과 무엇을 나란히 두는가)
손잡이        : 1) … 2) … 3) …   (각각 극단에서 무엇이 뒤집히는가)
숫자          : 1) … 2) … 3) …   (단위, 좋은 방향)
전제          :
결론          : ~할 때는 A, ~할 때는 B
시스템에서는  : OMS에서는 … | WMS에서는 …   (운영사별 설정이면 밝힌다)
이어 보기     : 선행 … / 다음 …
```

작성 예 — `order-routing`:

```
slug          : order-routing
질문          : 이 주문을 어느 창고에서 내보낼 것인가
정의          : 주문 라우팅(order routing)은 주문마다 물건을 내보낼 창고를 정하는 규칙이다
새로 나오는 말 : 주문 라우팅, 분할 출고(한 주문을 여러 창고에서 나눠 보내는 것), 배송 권역
처음이라면    : 가용 재고 → inventory-basics / 운영사·창고 → logistics-players / 계약 창고 → warehouse-assignment
비유          : 배달 앱이 주문을 가장 가까운 지점에 넘기는 것. 다만 물류는 지점마다 가진 재고가 다르다
형식          : 배정형
비교 대상     : 최단 거리 배정 vs 최저 비용 배정 vs 한 창고 몰아주기(분할 없음)
손잡이        : 1) 창고 간 재고 편중 — 치우칠수록 최단 거리 배정의 분할 출고가 늘어난다
                2) 주문당 품목 수 — 많을수록 분할 없는 배정의 납기 준수율이 떨어진다
                3) 권역 간 운임 차이 — 클수록 최저 비용과 최단 거리의 순위가 벌어진다
숫자          : 1) 건당 물류비(원, 낮을수록 좋음) 2) 약속 납기 준수율(%, 높을수록 좋음)
                3) 분할 출고율(%, 낮을수록 좋음)
전제          : 창고 3곳, 주문 10건, 운임은 권역 거리에 비례, 창고 처리 능력은 무제한으로 가정
결론          : 재고가 고르게 퍼져 있으면 가까운 창고에서 보내는 것이, 치우쳐 있으면 나눠 보내는 비용까지 따져 가장 싼 창고에서 보내는 것이 유리하다
시스템에서는  : OMS에서는 창고별 가용 재고 · 배송 권역 · 마감 시간을 입력으로 받는 배정 규칙이 되고, 규칙과 분할 허용 여부는 운영사마다 다르게 설정한다
이어 보기     : 선행 order-handoff, warehouse-assignment / 다음 allocation-atp, carrier-selection
```

## 기술 계약

홈과 다른 문서가 의존하는 부분이라 바꾸지 않는다.

- **파일**: `concepts/<slug>.html`, 외부 CSS·JS 없이 한 파일로 완결. slug는 ASCII 소문자와 하이픈.
- **완료 버튼**: `<button id="mv-done-btn" data-slug="<slug>">`. 클릭하면 `localStorage['mv-done:<slug>'] = '1'`을 저장한다. 홈이 이 키를 읽어 카드의 ✓ 배지와 트랙 진도 바를 그린다.
- **등록**: `data/catalog.json`의 `concepts`에 추가해야 홈에 보인다.
- **체험 패널**: SVG에 `role="img"`와 한글 `aria-label`, 상태 안내는 `aria-live` 한 곳 (`design-tokens.md`).

- [ ] 질문과 결론만 읽어도 물류를 모르는 사람이 뜻을 안다
- [ ] 새로 나오는 말이 5개 이하(첫걸음 트랙 3개 이하)이고, 처음 나오는 자리에서 용어집 문장으로 풀이했다

- [ ] 완료 버튼이 동작하고 홈에 ✓가 뜬다
